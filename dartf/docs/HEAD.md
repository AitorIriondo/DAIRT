# Grounding encoder/decoder

The head (6+6 layers, width 256) runs in fp16 TensorRT with its own fusions; its per-class cost is reduced by exact restructuring:

- **Prefix sharing.** Encoder layer 0's self-attention block depends only on the image. `export/split_ground_prefix.py` (K=1 export) and `export/split_ground_c16.py` (class-bucket export) produce a prefix engine (img_feat, img_pos → x1, pos; 3 ms per image) and a post engine that expands x1/pos to the K prompts of a bucket. K=16: 387 → 351 ms, bit-identical outputs. `runtime/eval_pipeline.py --ground <post.plan> --ground-pre <pre.plan>` evaluates the pair.
- **CUDA-graph replay.** `patches/runner_cuda_graph.patch` adds `LQ_CUDA_GRAPH=1` to the DART TensorRT runner: one capture of `enqueueV3`, replayed per call. Roughly 1 ms per engine call (trunk 164.0 → 162.6 ms).

`scripts/head_pipeline.sh` runs the split, the builds and the comparison against the monolithic bucket engine.

## Segmentation head (`demo/export_ground_mask.py`)

The DART grounding export emits scores, boxes and presence only; the SAM3 segmentation head also needs the last decoder layer's queries and the encoder's output (the pixel decoder replaces the coarsest FPN level with the encoder states, which are prompt-conditioned, and cross-attends them to the prompt). `export_ground_mask.py` re-exports the grounding bucket with two extra outputs, `hs` [K, 200, 256] and `enc` [5184, K, 256], and exports the head itself as `maskhead_qQ.onnx` with inputs `fpn_0`, `fpn_1` (bound directly to the vision engine's device buffers at run time), `enc`, `text_feats`, `text_mask` and `hs_sel` [K, Q, 256]. The prompt axis K is dynamic (`demo/build_mask_engine.py` builds an FP16 plan with a min/opt/max profile), so the head runs only for prompts that produced a detection, and only for the Q highest-scoring queries of each (Q = 32 by default). The outputs are the head's own logits at the 288 x 288 grid. The demo runner suppresses duplicates and nested parts by mask IoU and containment across prompts and queries, drops group boxes that contain two confident objects, and feeds the rest to a lightweight tracker (Hungarian matching on mask IoU with low-score continuation, short coasting, smoothed masks and a class vote per track), so labels and identities are stable from frame to frame; boxes are drawn from the smoothed masks. The text encoder runs once per prompt set; the detector head is image-conditioned and runs per frame.


### Mask head on the Orin, and its INT8 variant

Measured on the Orin (FP16, CUDA graph): 15.4 ms at one active prompt, 40.6 ms at four, 72.3 at eight; the pixel decoder runs once per prompt because the encoder states are prompt-conditioned, and one 3x3 convolution at 288x288 is 40 % of the time. `demo/quant_maskhead.py` puts calibrated Q/DQ (per-channel weights, per-tensor p99.99 activations from a few dumped frames, `demo/dump_maskhead_calib.py`) on the three pixel-decoder convolutions and leaves the rest in FP16; `demo/val_maskhead.py` compares two plans on held-out frames. Against the FP16 head the INT8 masks agree to 0.9945 mean IoU (0.944 min over 354 masks) with a pixel flip rate of 3e-5. Build the INT8 plan with `demo/build_mask_engine.py ... --int8`; on the Orin it runs in 8.5 / 29.3 / 57.4 ms at one / four / eight prompts (FP16: 15.4 / 40.6 / 72.3).

A second, exact rewrite (`export_ground_mask.py --phase-conv`) removes the upsample-then-convolve pattern: `conv3x3(fpn + nearest_up2(x))` equals `conv3x3(fpn)`, computed once per image, plus four 2x2 convolutions of `x` at half resolution whose taps are the 3x3 taps merged pairwise per output phase, followed by a pixel shuffle. It is exact to FP32 rounding (rel 2e-7) and needs 2.25x fewer multiply-adds in the two large convolutions; on the Orin it runs in 12.0 / 30.8 / 58.3 ms at one / four / eight prompts, 19 to 24 % less than the original FP16 head, at unchanged masks. The Q/DQ pass also applies to it but does not pay there (the 2x2 convolutions get slower INT8 kernels), so the choice is: exact phase head, or the INT8 original at four or more prompts.

### SAM3 native tracker in TensorRT

`demo/export_tracker.py` exports the SAM3 video tracker as three graphs with a static tensor contract: `trk_neck` (the tracker's own FPN on the ViT trunk output, which the vision engine exposes when built with `--mark-outputs '^permute_4$'`), `trk_init` (a mask prompt to an object pointer and a memory), and `trk_step` (memory attention over a dynamic number of memory frames and object pointers, the SAM mask decoder in multimask mode, and the memory encoder). The memory attention is re-expressed so that the memory length is dynamic; `--check` compares the wrapper with the reference `track_step` on real features (exact), and `demo/check_trk_trt.py` compares the TensorRT plans with that reference (FP16 rounding: mask IoU 0.9999). `demo/build_trk.py` builds the plans with named dynamic dimensions. `demo/sam3_track.py` drives them with the reference memory rules (conditioning frames, valid recent frames, pointer selection by recency).

Cost per propagation step: 5184 queries against up to seven memory frames per object, four layers. The first export (`trk_step`) runs in 66 ms on the Orin with seven memory frames. The second (`export_tracker.py --v2`, `trk_step_v2`) is the same mathematics with the memory passed as gathered tokens with valid-key counts and per-key rotary tables, and the first layer's self-attention and queries computed once per frame and broadcast to every object; it is exact against the reference. With the full memory it costs what the first export costs (Orin: 73 vs 67 ms per object with seven memory frames; RTX 4090: 13 vs 11 ms), so the gain of the gathered-key interface is what it makes possible: mask-guided key pruning (`--sam3-prune r`: keys within r cells of the object's mask plus a background grid) and an adaptive memory depth (`--sam3-adaptive`); at r=4 with a 1/4 background grid the memory keys drop to 30 % with no measurable change in identity churn over 15 s clips, so it is the default (`--sam3-prune 0` restores the full memory): **33 ms per propagated object on the Orin (25 ms with one memory frame, 29 ms per object in batches of four), 6 ms on the RTX 4090.** These are timings with real valid-key counts; trtexec reports about half of them for this engine because it feeds zero-filled inputs, and with `nvalid = 0` TensorRT's fused attention skips every masked tile.

Two further levers exist as options and are off by default because they change the tracker's behaviour rather than its implementation: change-gated refresh (`--refresh-iou` below 1: a seen object's memory is refreshed only when its detector mask moved, at least every `--refresh-max` frames) and query-side pruning (`export_tracker.py --v3`, `--sam3-qprune r`: the per-object memory attention runs only for the queries near the object's mask; 33 → 13 ms per object on the Orin, mask IoU 0.97 against the full step, but the object-score head loses the global context it uses to notice a vanished object, so it is not a substitute for the full step). The memory bank (memories, pointers, masks) is device resident: `demo/sam3_track.py` keeps it in CUDA tensors, gathers and prunes keys on the GPU and binds the engines to those tensors directly, so only the valid-key counts and per-object scalars cross the bus (on the 4090 this halved the per-frame propagation time). `demo/sam3_track_np.py` is the same driver without torch: raw CUDA buffers, a row-gather and a transpose kernel from `plugins/lq_util.cu`, and `trk_init288` (the init graph prompted with the head's 288-px logits); it matches the torch driver stage by stage and is what runs on the Orin. Each of its engine calls is replayed from a CUDA graph captured on the first use of a (shapes, addresses) key, with the key count rounded up to a 2048 bucket so shapes repeat (`LQ_KN_BUCKET`, `LQ_TRK_GRAPH=0` disables); the memory position rows are gathered on the device like the memory tokens, and memory-frame buffers come from a free list. Note on step v2: the pointer tokens are placed before the memory keys in the cross-attention, so the valid-count mask keeps every pointer and exactly `nvalid` memory keys; with the pointers last (the first export) an object with fewer keys than its batch-mates lost its last pointers, which made batched calls inexact (fixed, MOT17 HOTA 42.2 → 42.5). A custom single-head D=256 attention kernel (`plugins/lq_memattn_kernel.cuh`, exposed as the `LQMemAttn` plugin) was written and is correct, but TensorRT's fused attention is faster for this shape on both GPUs, so it is not used by default. The runner therefore uses it in a hybrid mode (`run_video.py --sam3-tracker`): detections and the lightweight tracker handle objects that are seen, conditioning memories are refreshed from detector masks every few frames (3 ms per object on the Orin), and propagation runs only for confirmed tracks the detector missed, under a per-frame budget (`--sam3-budget`, `--sam3-mem`). On dense clips the budgeted mode does not beat the lightweight tracker; it is meant for scenes with a few objects that get occluded.
